# SPEC — Barcode Inventory System

Source PRD: `Barcode_Inventory_System_PRD.md` (one-page outline). This document expands
that outline into an implementable spec. Anywhere this doc adds detail beyond the
original PRD, it is marked **[assumption]** — see §9 for the consolidated list.

---

## 1. Overview

A single company runs multiple branches (e.g. stores/warehouses). Each branch
periodically performs a physical inventory count. Staff walk the floor with a phone,
open the counting screen in their mobile browser, and scan product barcodes using the
device camera. The system records what was counted, compares it to the expected
quantity on file, and produces reports. Products without a printed barcode can have
one generated and printed as labels.

### Goals (from PRD)
- Fast inventory counting
- Mobile scanning (browser camera, no app install) **[assumption: confirmed by product owner]**
- Multi-branch support
- CSV export

### Out of scope (from PRD)
- POS
- Sales
- Accounting

---

## 2. Roles

| Role | Scope | Can do |
|---|---|---|
| **Super Admin** | Global | Everything below, plus manage branches, all users, all products/categories, view all reports across branches. |
| **Branch Manager** | One branch | Manage products/categories (global catalog, not branch-scoped — see §3.2 note), manage counters assigned to their branch, create/start/submit/approve/close inventory sessions for their branch, view/export their branch's reports. |
| **Counter** | One branch, assigned sessions only | View sessions they're assigned to that are `in_progress`, use the scanning screen, cannot approve/close sessions, cannot manage products or users. |

Enforced via `spatie/laravel-permission` roles: `super_admin`, `branch_manager`,
`counter`. Filament Policies gate every Resource and custom page.

**Note on Branch Manager + products:** the product catalog is shared across branches
(a product is the same item everywhere), but the *expected quantity* is per-branch
(§3.4). Branch Managers get full CRUD on the catalog because in a single-company setup
restricting catalog edits to Super Admin only tends to create bottlenecks. Revisit if
the product owner wants catalog changes centralized.

## 4. Screens (Filament resources unless noted)

1. **Branches** — Super Admin only. Standard CRUD.
2. **Users** — Super Admin manages all; Branch Manager can create/edit `counter` users
   scoped to their own branch only (policy-enforced).
3. **Categories** — Super Admin + Branch Manager.
4. **Products** — Super Admin + Branch Manager. Table shows barcode, name (locale-aware
   column), category, status. Row actions:
   - **Generate barcode** — if `barcode` is null, generates a unique Code128 value,
     sets `barcode_source = generated`.
   - **Print label** — adds product to a label sheet (single or bulk selection via
     table bulk action), renders a PDF via DomPDF with barcode image
     (`picqer/php-barcode-generator`) + product name, grid layout suitable for common
     label sheet stock (e.g. 3×8 Avery-style — exact layout is a Phase 4 detail, not
     a blocker).
5. **Product Branch Stock** — a simple per-branch editable grid/table
   (product × expected_quantity) instead of a generic Filament resource list, since
   Branch Managers will edit many rows in one sitting. Filterable by branch (Super
   Admin) or locked to own branch (Branch Manager).
6. **Inventory Sessions** — Branch Manager (own branch) + Super Admin (all branches).
   - List + create (draft) + assign counters + start + view live progress
     (counted lines so far, updated as counters scan) + submit review + approve/close.
   - Detail page shows the count lines table with expected / counted / variance,
     sortable/filterable by variance (e.g. "show only discrepancies").
7. **Scanning screen** — **custom Livewire page**, not a standard Filament resource
   page. Mobile-first, minimal chrome. See §5 for behavior. Accessible to `counter`
   role for sessions they're assigned to (status `in_progress`), and to Branch
   Manager/Super Admin for testing/oversight.
8. **Reports** — a dedicated Filament page (or section within Inventory Sessions) to
   run and export: session detail report, branch summary across a date range. See §7.

## 5. Core workflow: scanning

### 5.1 Entry
Counter opens their assigned, `in_progress` session from a simple list ("My Sessions").
Only one screen: scan, see running list, done.

### 5.2 Session status lifecycle
```
draft --(manager starts it)--> in_progress --(counter marks submitted, or
    manager does)--> submitted --(manager reviews & approves)--> approved --> closed
```
- `draft`: created, counters assigned, not yet visible to counters for scanning.
- `in_progress`: counters can scan. Counting can happen over multiple visits/days if
  needed — session stays open until explicitly submitted.
- `submitted`: counting finished, awaiting manager review. Counters can no longer add
  scans.
- `approved`: manager has reviewed variances and signed off. Read-only from here on.
- `closed`: archived state, same as approved but excluded from "active sessions" lists.

### 5.3 Camera scanning
- Uses `html5-qrcode` to access the device camera directly in the browser
  (`getUserMedia`) — requires HTTPS in production.
- Supports at minimum: EAN-13, UPC-A, Code128 (covers the vast majority of retail and
  internal barcodes).
- On a successful decode, the frontend calls a Livewire action with the raw barcode
  string — do not do the product lookup in JS.

### 5.4 Known barcode
- Look up `products.barcode`. If found and `status = active`:
  - Ensure an `inventory_count_lines` row exists for (session, product); create it with
    `expected_quantity_snapshot` copied from `product_branch_stock` if this is the
    first scan of that product in this session.
  - Increment `counted_quantity` by 1, log a `scan_events` row.
  - Update the on-screen running list (product name, quantity so far) — this list is
    the counter's main feedback loop, keep it fast and simple.
  - Give a short audible/visual confirmation (beep/flash) so the counter doesn't need
    to look at the screen after every scan.

### 5.5 Unknown barcode
- If no product matches the scanned code, prompt: "Unknown barcode — add new product?"
  - If yes: quick-create form (name_en, name_ar, category, unit) inline, without
    leaving the scanning screen. Save with `status = pending_review`,
    `barcode_source = existing` (it came from a real physical label), and immediately
    create a count line + scan event for it, same as §5.4.
  - A Branch Manager later reviews all `pending_review` products (a filter on the
    Products list) and flips them to `active` (or corrects/merges them).
  - Counters can create `pending_review` products but cannot set `active` status
    directly — enforce via policy.

### 5.6 Manual adjustment
- A counter (or manager) can manually edit `counted_quantity` on a line instead of
  scanning repeatedly (e.g. "I counted 40 units, I'm not scanning 40 times"). Manual
  edits require a short required `notes` entry for audit purposes and are visually
  distinguished in the UI from scan-derived counts.

### 5.7 Hardware barcode scanner fallback **[assumption — nice-to-have, not a blocker]**
Dedicated USB/Bluetooth barcode scanner guns commonly emulate keyboard input
("keyboard-wedge"). Add a plain text input on the scanning screen, auto-focused, that
accepts a pasted/typed barcode followed by Enter, feeding the same lookup logic as
§5.3–§5.5. This costs very little to add and makes the system usable with real scanner
hardware later without building a native app. Treat as low priority — implement after
camera scanning is solid (see `tasks.md` Phase 6).

## 6. Variance / discrepancy handling

- `variance = counted_quantity - expected_quantity_snapshot`, computed per count line.
- On the session detail/approval screen, surface a filter/sort for "variance ≠ 0" so a
  manager can review discrepancies quickly before approving.
- No automatic stock correction happens anywhere — this system does not write back to
  a POS/accounting system (explicitly out of scope). Approving a session just locks it.
- **[assumption]** A configurable variance threshold (e.g. flag anything beyond ±5%)
  is a reasonable v2 addition but is not required for MVP — for MVP, simply show all
  non-zero variances.

---

## 7. Reports & export

1. **Session detail report** — one row per count line: product (name/SKU/barcode),
   expected, counted, variance, last scanned by/when. Exportable as CSV
   (`maatwebsite/excel`) and viewable on-screen. This directly satisfies the PRD's
   "CSV export" goal.
2. **Branch summary report** — across a date range, per branch: number of sessions,
   total items counted, total variance, count of products with `pending_review`
   status still unresolved. CSV export.
3. Reports respect role scope: Branch Manager sees only their branch; Super Admin can
   filter by any/all branches.

## 8. Non-functional requirements

- **Bilingual EN/AR with RTL.** Every screen must render correctly in Arabic RTL,
  including the scanning screen and printed labels/reports.
- **Mobile-first scanning screen.** Large touch targets, minimal scrolling, works well
  one-handed while holding a phone with the other hand doing the scanning motion.
- **HTTPS required** for camera access in production (cPanel hosting — confirm SSL is
  configured before this feature is demoed).
- **Barcode uniqueness** enforced at the DB level (`unique` index on `products.barcode`).
- **Auditability** — `scan_events` is append-only and is never edited or deleted; it's
  the source of truth if a `inventory_count_lines.counted_quantity` value is ever
  disputed.

## 9. Assumptions made to fill PRD gaps (confirm/override as needed)

The PRD was a one-page bullet outline with no data model, roles, or workflow detail.
The following were decided by the product owner during scoping and are treated as
final for MVP:

1. Scanning is via **browser camera only** (`html5-qrcode`), no native app.
2. This is a **single company with multiple branches**, not a multi-tenant SaaS.
3. The system **does generate and print barcodes** for products that don't have one.
4. Three roles: Super Admin, Branch Manager, Counter (not in original PRD, added
   because "Users" was listed in scope with no detail).
5. A per-branch "expected/system quantity" is tracked so counts can be compared
   against something (not in original PRD — otherwise "reports" would have nothing
   to report beyond a raw count list).
6. Product catalog is shared across branches; only expected quantity is per-branch.
7. Hardware keyboard-wedge scanner support is included as a low-priority fallback,
   not a primary requirement.
8. No queue/worker infrastructure required for MVP — PDF/CSV generation runs
   synchronously, matching the cPanel shared-hosting deployment target.

If any of these don't match intent, update this section and the affected parts of
the spec before the agent implements the related phase.
